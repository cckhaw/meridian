# TMF620 Product Catalog Management

Meridian's catalog is served as a TM Forum **TMF620 (v4 profile)** API, so a catalogue designer, a partner portal or another BSS can read and write it over the standard interface. It sits on the same code as the **Catalog** screen: every write goes through `createNode`, `updateNode`, `moveNode`, `setStatus` and `deleteNode`, so the same rules apply (a sold offer cannot be repriced, a SKU is reserved once, a prerequisite must exist, a scheduled offer needs a future date). Nothing here bypasses them.

Base path: `/api/tmf-api/productCatalogManagement/v4`. Authentication, signing, rate limits and the TM Forum error shape are those of the northbound gateway ([INTEGRATION_API.md](INTEGRATION_API.md)). Scopes: **`catalog:read`** and **`catalog:write`** (add them to an OAuth client in Settings → Integration).

## Resources

| Resource | Meridian | Operations |
|---|---|---|
| `catalog` | the one catalogue, `meridian`; its categories are the network types | GET |
| `category` | network type → category → group | GET (list, one), POST, PATCH, DELETE |
| `productOffering` | an offer | GET (list, one), POST, PATCH, DELETE |
| `productSpecification` | what an offer includes: its line items; same id as the offer | GET (list, one), PATCH |
| `productOfferingPrice` | one price of an offer (see below) | GET (list, one), POST, PATCH, DELETE |

Lists take `offset` (0 to 10,000) and `limit` (up to 100) and answer `X-Total-Count`, `X-Result-Count`, `X-Offset`; `fields=a,b` keeps those attributes (plus `id`, `href`, `@type`). Filters: `lifecycleStatus`, `category.id`, `name`, `kind` and `lastUpdate.gt` (offerings: handy for "what changed since I last synced"); `parentId`, `isRoot` (categories); `productOffering.id`, `priceType` (`oneTime`, `recurring`, `usage`) and `lifecycleStatus` (prices).

## Mapping

| TMF620 | Meridian |
|---|---|
| `lifecycleStatus` **In design** | Draft; with a future `validFor.startDateTime`, Scheduled (go-live date) |
| **Active** / **Retired** | Active / Retired (also accepted: Launched → Active, Obsolete → Retired, In study and In test → In design) |
| `category[0]` | the group the offer sits in (changing it moves the offer) |
| `productOfferingPrice[]` | price components: `oneTime`, `recurring` (month or year), `usage`; `taxIncludedAmount` or `dutyFreeAmount` as `{unit, value}` in major units (`5.50`), stored as minor units |
| `productOfferingTerm[]` | contract: 12, 24 or 36 months; none = no contract |
| `productOfferingRelationship[]` | `dependency` = *customer must first have*, `exclusivity` = *cannot be bought together with*; the target is an offer or a group/category ("any offer in") |
| `channel[]`, `place[]` | sales channels, markets (ISO-3166 alpha-2) |
| `productSpecification` characteristics | line items: name, value + `unitOfMeasure`, `@meridian.itemType`, `unlimited`, `sku` |
| `@meridian` | what TMF620 has no place for: `kind` (offer type id, **required on create**), `fulfilment`, `characteristics`, `partnerCode`, `validityDays`, `ocs`, `variants`, `deals`, `suspension`, `group`, `contract` details (early termination, subsidy) |

An offering read and written back unchanged changes nothing. A root `category` is a network type and needs `@meridian.networkType` (`mobile`, `fiber`, `iot`, `none`); the level of any other category follows its parent (network type → category → group). A group holds offerings, not categories.

## Writing

* **POST** creates. `id` may be supplied (lowercase letters, digits, dashes) and makes the call safe to retry: a second POST with the same id answers **409** rather than creating a duplicate. Without an id one is made from the name.
* **PATCH** is a merge patch: only the attributes named change. Arrays replace the whole list. A change of price, term or `@meridian.kind` on an offer that has been sold is refused (422): create a new offering and retire the old one.
* **PATCH productSpecification** with `productSpecCharacteristic` sets the complete list of line items: matching `id` updates, no id adds, a missing one is removed.
* **DELETE** follows the catalog's rule: empty, never sold, not used as a dependency. Otherwise set `lifecycleStatus` to Retired.

Errors use the TM Forum shape (`code`, `reason`, `message`, `status`); catalog rule violations list every rule broken.

## Prices as a resource

An offering still carries its prices in `productOfferingPrice[]`, and each entry now has a stable `id` and an `href`. The same price is also a resource of its own at `/productOfferingPrice/{id}`, which is what a pricing tool edits: change one price without sending the rest of the offering.

* In Meridian a price belongs to exactly one offering and is stored with it. A price resource therefore carries `productOffering: { id, href }` (an extension; the v4 resource has no back-reference), takes its `lifecycleStatus` and `validFor` from the offering, and `version` and the `ETag` are the offering's. A change to one price changes the offering's version, so an `If-Match` taken from any read of the offering or one of its prices is checked against the offering as a whole: it can refuse a write that would have been harmless, never accept one that overwrites.
* **POST** `/productOfferingPrice` adds a price to the offering named in `productOffering.id` (required). `id` may be supplied (lowercase letters, digits, dashes, up to 70; **409** when taken anywhere in the catalogue); without one the next free `<offering>-price-<n>` is used. The body is the price as in the offering: `priceType`, `price.taxIncludedAmount` or `price.dutyFreeAmount` as `{unit, value}`, and for `recurring` the `recurringChargePeriodType` / `recurringChargePeriodLength`.
* **PATCH** is a merge-patch: `priceType`, the period, and `price`. A `price` that names only the amount (`{"taxIncludedAmount": {"value": 7.5}}`) keeps the unit and the tax treatment.
* **DELETE** removes a price; an offering keeps at least one (add the new one first, or delete the offering).
* All of it goes through the offering's own update, so its rules hold: **a sold offering cannot be repriced** (add, change and delete are refused with 422, the same as a price change on the offering), the currency must be known, the offering's events are raised (`OFFERING_CHANGED` with `changedAttributes: ["productOfferingPrice"]`), and the ETag moves.
* **Ids.** The id is stored with the price the first time an offering's prices are written through TMF620 (create, a PATCH of the offering that sends `productOfferingPrice`, or any price write) and stays when other prices are added or removed. Before that a price has a positional id, `<offering>-price-<n>` counting from its place in the list, the same every time it is read. Prices written on the Catalog screen or by the CSV import keep the ids they have; one added there has no id until a TMF620 write, and then takes the next free `<offering>-price-<n>`. Sending the offering back with its price ids does not count as a repricing; a PATCH of the offering that sends `productOfferingPrice` without ids keeps the ids by position.

## Concurrent edits: ETag and If-Match

Every resource read by id (`category/{id}`, `productOffering/{id}`, `productSpecification/{id}`) and every successful write answers with an `ETag` header: the node's version in quotes (`"7"`). The version goes up with every change to the node, and also when what an offer includes changes (a line item added, changed, removed or reordered, which is a change of its specification) or when the node is moved, so the ETag changes exactly when the resource does. An offering and its specification share the id and the ETag.

* `If-Match` on `PATCH` and `DELETE` says "only if it is still as I read it". A stale value answers `412` with the TM Forum error `PRECONDITION_FAILED` and changes nothing, so two editors who both read version 5 cannot overwrite each other: the second one re-reads and repeats the change. `If-Match: *` means "if it exists"; a list of ETags and weak validators (`W/"5"`) are accepted. With no `If-Match` the write goes ahead unconditionally, as HTTP allows, so a client that wants protection has to send it.
* The check is made inside the write, under a row lock in one transaction, so it cannot be split by a concurrent writer. Every TMF620 write is now one transaction, which also means a `PATCH` that changes attributes, category and lifecycle together happens completely or not at all.
* `If-None-Match` on a read answers `304 Not Modified` (no body, the `ETag` header) while nothing changed, which makes polling cheap.
* Lists have no ETag; read the `version` of each item, or follow the events below.

## Events

Every change to the catalogue raises a TMF620 event, whether it was made through this API, the Catalog screen or the bulk offers import. The event is written to the outbox in the same transaction as the change and travels through the normal event hub ([INTEGRATION_API.md](INTEGRATION_API.md#events)): outbound webhooks, TM Forum 688 listeners (`POST /api/tmf-api/eventManagement/v4/hub` with `query=eventType=ProductOfferingStateChangeEvent`, scope `event:subscribe`) and event topics all receive them. Like the other high-volume events they are only written while somebody listens (the listener list is looked at every few seconds).

| Business event | Announced as | When |
|---|---|---|
| `OFFERING_CREATED` / `CATEGORY_CREATED` | `ProductOfferingCreateEvent` / `CategoryCreateEvent` | a node is created |
| `OFFERING_STATE_CHANGED` / `CATEGORY_STATE_CHANGED` | `ProductOfferingStateChangeEvent` / `CategoryStateChangeEvent` | the lifecycle changes: In design, Active, Retired, including a scheduled go-live arriving |
| `OFFERING_CHANGED` / `CATEGORY_CHANGED` | `ProductOfferingAttributeValueChangeEvent` / `CategoryAttributeValueChangeEvent` | an attribute changes, a node is moved, a go-live date changes, or one of an offer's line items is added, changed or removed |
| `OFFERING_DELETED` / `CATEGORY_DELETED` | `ProductOfferingDeleteEvent` / `CategoryDeleteEvent` | a never-sold node is deleted |

The body is the standard envelope (`eventId`, `eventTime`, `eventType`, `domain: "productCatalogManagement"`, `event: { productOffering | category: {...} }`). The resource carries `id`, `href` (a path on this deployment), `name`, `version` (the node's version, which goes up with every change, so a consumer can tell which catalogue version is live), `lifecycleStatus`, `lastUpdate`, `category` (the offering's group) or `parentId` (a category's parent), `validFor.startDateTime` for a scheduled node, and, per event: `previousLifecycleStatus` on a state change and `changedAttributes` on an attribute change. `changedAttributes` uses the TMF620 names (`productOfferingPrice`, `productOfferingTerm`, `productOfferingRelationship`, `channel`, `place`, `category`, `productSpecification`, `validFor`, `name`, `description`) and `@meridian.<field>` for what TMF620 has no place for. A line item is announced as its offering (`productSpecification` changed). The event holds no prices, terms or other content: read the resource with the id and href.

## Not covered yet

`bundledProductOffering` (a family or shared plan keeps its members and limits in `@meridian.group`; a TMF620 bundle has component offerings with cardinalities, so the two do not map one to one and a write that appeared to work but did not would mislead), `productOfferingRelationship` types other than dependency and exclusivity, price events of their own (a price change is an `OFFERING_CHANGED` of its offering), and price constraints, tariffs and `popRelationship`. The custom `/api/catalog` routes and the CSV import are unchanged, and the Catalog screen keeps using them.
